# AWC Standards Interoperability — Implementation v0.1

**Status:** experimental, sandbox-only. This document describes real code and tested transformations, not formal protocol certification. Date: November 1, 2026.

## Purpose and boundaries

AWC continues to own *who undertook what obligation, on whose authority, backed by whose economic exposure and evidenced by which outcomes*. It should not replace existing protocols for policy expression, identity, asset description, asynchronous execution, procurement, payment settlement, or provenance.

The normative reference material is in [standards-adoption-research.md](standards-adoption-research.md).

The CLI prints per-scenario counts and decisions, not private data.

MCP clients: `operations.standards` accepts `{"scenario":"vending"|"cloud"|"plant"}` and returns a complete synthetic standards bundle. The read-only reference resource `awc://standards/manifest` advertises implemented mappings. Existing `operations.simulate` continues to return a small operating dashboard.

### AuthZEN localhost test

The Cloudflare Worker exposes `/.well-known/authzen-configuration` and `POST /access/v1/evaluation` only if both conditions hold:

- Request host is `localhost` or `127.0.0.1`.
- Local sandbox is explicitly enabled and the separately provisioned MCP buyer token is authenticated.

The resolver only loads **server-generated fictional proposals** from the built-in scenarios. It does not accept a caller-supplied mandate, resource owner grant, policy, time or cost balance as authoritative. The local buyer token is explicitly mapped to the fictional demo manager for interoperability tests only.

Example test using a valid fixture generated by the code:

```ts
const report = await runStandardsScenario("vending");
const request = actionToAuthzen(report.syntheticReadProposal);
// POST to local-only /access/v1/evaluation using a private sandbox token.
// A telemetry.read returns decision:true; a commercial write is decision:false
// until the independent work/purchase commit flow is satisfied.
```

**Do not publish this local PDP as a production AuthZEN service.** A production implementation needs its own registered audience, trustable token identity and scopes, immutable proposal registry, policy and asset-owner stores, decision freshness, audited PEP enforcement, and payment/account reservation. The existing code rejects all production-host AuthZEN requests with 404.

## Important semantic rules

1. ODRL is an expressible policy document, **not** a cryptographic authorization token or standalone legal service agreement. Unsupported operators/extensions don't create permissions; the AWC parser only accepts its own exact limited profile.
2. AuthZEN's single boolean response cannot itself express a safe conditional purchase. Conditional `permit-with-conditions` therefore maps to `decision:false` plus diagnostic context; only a subsequent independent commit service can reserve cash and carry out an allowed action.
3. COAZ-MCP is a **draft**. The included safe subset maps `tools/call` into AuthZEN using the verified caller subject/agent identity, and rejects unknown tools or object-sensitive mutations until the application performs its own policy check.
4. CloudEvents replay is identified by source+event ID, with a monotonic **AWC extension** `awcsequence`. This sequence is application-defined and requires a persistent single-authority transaction log to generalize.
5. PROV-O graphs describe provenance but do not verify signatures or truth. A simulated ActionReceipt must never be presented as an independently verified Attest credential or settled financial receipt.
6. OpenSLO projections describe what to measure but do not query live telemetry or assert compliance. A **metric threshold is not a reliability target**; the adapter requires an explicitly supplied `reliabilityTarget`. The demo uses a fictional 99% error-budget target. Without one, no SLO is exported. Missing/stale measurements remain unknown.
7. OSB 2.17 provisioning has an external side effect that may cost money. The adapter produces only a preview and never sends an HTTP write. OSB catalogs do not guarantee price or lease-expiry support, so the broker must obtain authoritative quotes and handle ongoing cost.
8. UBL 2.4 example export doesn't constitute a purchase, accepted order, tax document or payment. A production adapter must use normative XSD/code lists and jurisdiction-specific review.

## Acceptance and negative tests

- ODRL documents round-trip without broadening actions, identities, target assets, time, obligations or budget. Tampered/unknown policies are rejected.
- AuthZEN denies missing proposal, wrong verified subject, altered exact revision, revoked mandate, missing asset permission and conditional writes.
- COAZ tool authorization fails closed on tool unknown, missing scope, denial, PDP outage or object-sensitive mutation.
- CloudEvents deduplicates exact replay and rejects altered event IDs and missing sequences.
- PROV-O ties agent to accountable party and accepted action evidence; mismatched proposal/receipt identities fail.
- OpenSLO refuses unsupported obligation types/operators and windows.
- OSB rejects unknown plan, expired authorization, wrong provider and non-HTTPS metadata endpoints.
- UBL XML escapes product names and requires bounded positive quantities/correct money.
- Synthetic scenarios have no external side effects and demonstrate safe read, conditional restock, denied physical command and escalated scheduling.

## Next standard-native workstreams

2. Add ODRL restricted policy signatures / issuer authority and regression suite testing equivalence against an independent policy engine.
3. Durable CloudEvents inbox/outbox and provenance/Attest VC issuance, with issuer key status and privacy.
4. OSB 2.17 real provision/status/deprovision adapter with **verified** resource leases, accounting and orphan cleanup under strict risk/budget policy.
5. UBL XSD-validated purchase orders plus accepted responses, UCP checkout and optional GS1 EPCIS physical-goods movement from authoritative data.
6. Asset discovery through WoT/AAS/OPC UA in read-only deployments and qualified site review before any operational changes.
